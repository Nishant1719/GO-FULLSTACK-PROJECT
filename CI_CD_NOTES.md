## CI/CD pipeline (current implementation)

The project uses GitHub Actions at `.github/workflows/aws-deploy.yml` for a **demo-style but cloud-realistic** stack:

- **Terraform**: VPC, public/private subnets, ECR repositories, RDS PostgreSQL (private subnets), EC2 (Docker host in a public subnet), SSM Parameter Store for the database URL.
- **ECR**: CI builds and pushes three Docker images with automatic tags.
- **EC2**: Systems Manager Run Command pulls those images and runs `docker compose` using [`infra/deploy/docker-compose.aws.yml`](infra/deploy/docker-compose.aws.yml).

The current application version in the repo is `0.1.0` for both `frontend/` and `bff-node/`.

### Branch and environment mapping

| Branch | GitHub Environment | Terraform variables file | Artifact tag pattern | Purpose |
|--------|---------------------|--------------------------|----------------------|---------|
| `dev`  | `development`       | `infra/terraform/environments/dev.tfvars`  | `dev-<shortsha>`  | Shared development deployment |
| `main` | `production`        | `infra/terraform/environments/prod.tfvars` | `prod-<shortsha>` | Production deployment |

Feature work should land in `dev` first. Promotion from `dev` to `main` is the release path to production.

### Trigger behavior

1. **CI** — Go tests, frontend lint/build, BFF `npm ci`.
2. **Terraform** — Applies `infra/terraform` (VPC, ECR, RDS, EC2, DB URL in SSM).
3. **Publish** — Builds and pushes Docker images to the ECR repos created by Terraform.
4. **Deploy** — Runs [`infra/deploy/ssm_deploy.py`](infra/deploy/ssm_deploy.py) to execute a remote script on EC2 via SSM: ECR login, write `.env`, `docker compose pull` / `up`.

`workflow_dispatch` is enabled for manual execution.

### Automatic artifact versioning

No manual image tag renaming is required.

The workflow generates Docker tags automatically from the branch and commit SHA:

- `dev` branch → immutable tag like `dev-a1b2c3d`
- `main` branch → immutable tag like `prod-e4f5g6h`

It also publishes moving tags `dev-latest` and `prod-latest` for convenience. Prefer the immutable tag for traceability.

### What Terraform provisions

- **Networking**: VPC, internet gateway, two public subnets (EC2), two private subnets (RDS), route tables.
- **ECR**: `go-fullstack-frontend`, `go-fullstack-bff`, `go-fullstack-go-api`.
- **RDS**: PostgreSQL 16 in private subnets; password generated by Terraform; connection string stored in SSM at `/go-fullstack/<environment>/database_url`.
- **EC2**: Amazon Linux 2023, Docker and Docker Compose plugin via user data, IAM instance profile for ECR pull, SSM, and reading the DB URL parameter.

Terraform outputs include `app_url` (HTTP to the instance public IP), `ec2_instance_id`, `ecr_registry_url`, and `database_url_parameter_name`.

### Required GitHub environment configuration

Create GitHub Environments:

- `development`
- `production`

For each environment (`development`, `production`), open **Settings → Environments → [environment name]** and add:

- **Variable** `AWS_REGION` — e.g. `us-east-1` (you can use a different region per environment if you want).
- **Variable** `AWS_ROLE_ARN` — ARN of the IAM role GitHub Actions assumes via **OIDC** (e.g. `arn:aws:iam::123456789012:role/github-actions-go-fullstack`). Use a different role per environment if you want separate dev/prod trust or permissions.

You can set the same variables at **repository** level instead if one region and one role apply to all jobs.

### AWS OIDC and IAM role

In AWS (one-time per account; often done by an admin):

1. **IAM → Identity providers**: add **OpenID Connect** with URL `https://token.actions.githubusercontent.com` and audience `sts.amazonaws.com` (see [GitHub’s AWS OIDC guide](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/configuring-openid-connect-in-amazon-web-services)).
2. **IAM → Roles**: create a role **trusted by the GitHub OIDC provider**. The trust policy must allow `sts:AssumeRoleWithWebIdentity` and restrict the `sub` claim to this repo (and branch/environment if desired), e.g. `repo:OWNER/REPO:ref:refs/heads/dev` or conditions for GitHub Environments.
3. Attach permission policies to that role so the pipeline can run Terraform, push to ECR, and call SSM (see below).

The workflow uses `permissions: id-token: write` and `aws-actions/configure-aws-credentials` with `role-to-assume: ${{ vars.AWS_ROLE_ARN }}` — no long-lived AWS access keys in GitHub.

### IAM permissions for the CI role

The IAM **role** assumed via OIDC must be allowed to:

- **Terraform**: VPC, EC2, RDS, ECR, SSM, IAM (for instance profile / policies as defined in Terraform).
- **ECR**: push images and login.
- **SSM**: `ssm:SendCommand`, `ssm:GetCommandInvocation`, `ssm:ListCommandInvocations` (and related read APIs for the deploy job).

For a demo, **AdministratorAccess** on that role is simplest; tighten later for production.

**Security:** scope the role trust policy to this repository (and optionally branch/environment); avoid broad `repo:ORG/*` unless intentional.

### Database migrations

On startup, the Go API runs **`golang-migrate`** against SQL files under [`go-domain/migrations/`](go-domain/migrations/) (see [`internal/database/migrate.go`](go-domain/internal/database/migrate.go)). The container uses `./migrations` relative to the image workdir (`/app`). Override with **`MIGRATIONS_PATH`** if needed; set **`SKIP_MIGRATIONS=true`** only for debugging (not recommended in production).

RDS URLs from Terraform use `sslmode=require`, which works with the bundled `lib/pq` driver.

### Summary

The pipeline authenticates to AWS with **OIDC** (GitHub assumes an IAM role via `AWS_ROLE_ARN`; no static access keys in GitHub), validates code, provisions **EC2 + RDS + ECR** with Terraform, publishes versioned images to ECR, and deploys them on the EC2 host with **Docker Compose** and **SSM**, using the RDS connection string from SSM.
